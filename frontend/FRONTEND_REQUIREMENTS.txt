--------------------------------------------------------------------------------
1. EXECUTIVE ARCHITECTURE OVERVIEW
--------------------------------------------------------------------------------
The OBSIDIAN frontend is a luxury editorial digital commerce platform built on
Next.js (App Router, Turbopack, React 19). It interfaces directly with the 
OBSIDIAN Express/TypeScript backend API.

KEY ARCHITECTURAL RULES:
1. Pure Supabase Authentication:
   - Primary user identity is the authenticated Supabase UUID (`auth.uid()`).
   - The frontend communicates with the backend via standard HTTP Bearer tokens:
     `Authorization: Bearer <supabase_access_token>`.
   - No custom JWT signing or Auth0 tokens are permitted.
2. Canonical Profile Table:
   - The user profile is canonically synchronized in `public.profiles` linked to
     `auth.users(id)`.
   - Read operations do NOT create or write user records.
   - Profile sync only occurs on signup, login, or explicit `/api/auth/sync`.
3. High Performance & Zero Database Polling:
   - Real-time updates occur via Server-Sent Events (`EventSource` on `/api/stores/:id/realtime`).
   - Dashboard hydration is unified via `GET /api/account/state`.
   - Liveness checking uses lightweight `GET /health` (0ms DB load).

4. AUTHENTICATION & IDENTITY ARCHITECTURE (SUPABASE AUTH)
--------------------------------------------------------------------------------
1. Token Storage & Lifecycle:
   - The frontend stores the active Supabase JWT in `localStorage`:
     * `obsidian_token`: Raw access token string
     * `obsidian_session`: JSON object `{ access_token, token_type, user }`
2. Authentication Headers:
   - All protected backend API requests must provide:
     `Authorization: Bearer <supabase_access_token>`
   - For Server-Sent Events (SSE) where custom headers are unsupported by browser
     `EventSource`, append the token as a query parameter:
     `GET /api/stores/:id/realtime?token=<supabase_access_token>`
3. Identity Mapping:
   - Frontend components use the Supabase User UUID as `user.id`.
   - Never use email as a database primary key.
   - User roles default to `'merchant'`.
4. Authentication Flows:
   - Signup: `POST /api/auth/signup`
   - Login: `POST /api/auth/login` (supports email/password or Supabase Bearer token)
   - Profile Verification: `GET /api/auth/me`
   - Explicit Profile Sync: `POST /api/auth/sync`
   - Password Update: `POST /api/auth/update-password`

5. COMPLETE BACKEND API SPECIFICATION & FRONTEND CONTRACTS
--------------------------------------------------------------------------------

A. SYSTEM & HEALTH
- GET /health
  * Lightweight liveness probe (0ms DB query).
  * Returns: `{ "status": "ok", "service": "obsidian-backend", "timestamp": "...", "environment": "..." }`
- GET /health/db
  * Dedicated Supabase connectivity probe.
  * Returns: `{ "status": "ok", "service": "obsidian-backend", "database": "connected", ... }`
- GET /api/docs/swagger.json
  * Full OpenAPI 3.0.3 specification.

B. AUTHENTICATION & ACCOUNT
- POST /api/auth/signup
  * Request Body: `{ "email": string, "password": string, "full_name"?: string }`
  * Response: `{ "message": string, "user": UserDTO, "token": string, "session": object }`
- POST /api/auth/login
  * Accepts: `{ "email": string, "password": string }` OR Bearer token in header
  * Response: `{ "message": string, "user": UserDTO, "token": string, "session": object }`
- GET /api/auth/me
  * Header: `Authorization: Bearer <token>`
  * Response: `{ "user": { "id": string, "email": string, "full_name"?: string, "avatar_url"?: string, "role"?: string } }`
- POST /api/auth/sync
  * Header: `Authorization: Bearer <token>`
  * Response: `{ "message": string, "user": UserDTO }`
- POST /api/auth/update-password
  * Header: `Authorization: Bearer <token>`
  * Request Body: `{ "password": string }`
  * Response: `{ "success": boolean, "message": string }`

C. UNIFIED DASHBOARD STATE & HYDRATION
- GET /api/account/state
  * Header: `Authorization: Bearer <token>`
  * Description: Single source of truth for dashboard state. Replaces multiple requests.
  * Response:
    ```json
    {
      "success": true,
      "user": { "id": "...", "email": "...", "fullName": "...", "ownerName": "..." },
      "store": { "id": "...", "name": "...", "slug": "...", "currency": "₹", "businessType": "...", ... },
      "products": [ { "id": 1001, "name": "...", "price": 99.99, "stock": 10, "emoji": "📦", ... } ],
      "orders": [ { "id": 5001, "customerName": "...", "total": 99.99, "status": "pending", "date": "..." } ],
      "analytics": { "totalSales": 999.9, "totalOrders": 12, "uniqueCustomers": 8, "chart": { ... } }
    }
    ```
- PUT /api/account/state
  * Header: `Authorization: Bearer <token>`
  * Request Body: `{ "store"?: object, "products"?: array, "orders"?: array }`
  * Response: `{ "success": true, "message": string, "state": DashboardStateDTO }`
- POST /api/account/import-local-state
  * Header: `Authorization: Bearer <token>`
  * Description: One-time migration endpoint from browser `localStorage` into PostgreSQL.
  * Request Body: `{ "store": object, "products": array, "orders": array }`
  * Response: `{ "success": true, "message": string, "state": DashboardStateDTO }`

D. STORE OPERATIONS
- GET /api/stores/me
  * Header: `Authorization: Bearer <token>`
  * Response: `{ "stores": StoreDTO[], "store": StoreDTO, "defaultStore": StoreDTO }`
- POST /api/stores
  * Header: `Authorization: Bearer <token>`
  * Request Body:
    ```json
    {
      "name": "My Boutique",
      "business_type": "fashion",
      "currency": "INR",
      "address": "123 Fashion Street, Mumbai",
      "latitude": 19.0760,
      "longitude": 72.8777,
      "selected_template_id": "obsidian-classic"
    }
    ```
- GET /api/stores/:id
  * Response: `{ "store": StoreDTO, "formattedStore": StoreDTO }`
- PATCH /api/stores/:id
  * Request Body: Partial Store fields (name, description, contact_email, phone, etc.)
- PATCH /api/stores/:id/location
  * Request Body: `{ "latitude": number, "longitude": number, "formattedAddress"?: string, "placeId"?: string }`
- POST /api/stores/:id/select-template
  * Request Body: `{ "templateId": string }`
- POST /api/stores/:id/upload
  * Header: `Authorization: Bearer <token>`
  * Request: `multipart/form-data` with fields:
    * `file`: Binary image (JPEG, PNG, WebP, SVG; max 5MB)
    * `category`: `'logo'` | `'banner'` | `'product'`
    * `productId` (optional): Numeric or UUID product identifier
  * Response: `{ "message": string, "url": string, "path": string }`

E. PRODUCT CATALOG
- GET /api/stores/:id/products
  * Query parameters: `?search=...&category=...&status=active`
  * Response: `{ "products": FrontendProductDTO[], "rawProducts": ProductRecord[] }`
- POST /api/stores/:id/products
  * Header: `Authorization: Bearer <token>`
  * Request Body:
    ```json
    {
      "id": 1001,
      "name": "Luxury Silk Robe",
      "price": 149.99,
      "discountPrice": 129.99,
      "stock": 15,
      "emoji": "👘",
      "category": "Apparel",
      "description": "Pure mulberry silk robe",
      "image": "https://..."
    }
    ```
- PUT /api/stores/:id/products/:productId
  * Header: `Authorization: Bearer <token>`
  * Accepts numeric `client_id` or UUID for `:productId`
- PATCH /api/stores/:id/products/:productId/stock
  * Header: `Authorization: Bearer <token>`
  * Request Body: `{ "delta"?: number, "stock"?: number }`
  * Instant inventory increment/decrement (e.g. `delta: -1` on purchase, `delta: +10` on restock).
- DELETE /api/stores/:id/products/:productId
  * Header: `Authorization: Bearer <token>`

F. ORDER MANAGEMENT
- GET /api/stores/:id/orders
  * Header: `Authorization: Bearer <token>`
  * Response: `{ "orders": FrontendOrderDTO[], "rawOrders": OrderRecord[] }`
- POST /api/stores/:id/orders
  * Public buyer endpoint (no auth required for checkout).
  * Supports Nested Line Items (Cart Checkout) or Legacy Single Product:
    ```json
    {
      "customerName": "Alice Smith",
      "customerEmail": "alice@example.com",
      "customerPhone": "+91 9876543210",
      "customerAddress": "42 Ocean Drive, Mumbai",
      "paymentMethod": "Cash on Delivery",
      "items": [
        {
          "productId": 1001,
          "name": "Luxury Silk Robe",
          "quantity": 2,
          "unitPrice": 129.99,
          "emoji": "👘"
        }
      ],
      "total": 259.98
    }
    ```
  * Response: `{ "message": "Order placed successfully", "order": FrontendOrderDTO, "remainingStock": 13 }`
- PATCH /api/stores/:id/orders/:orderId/status
  * Header: `Authorization: Bearer <token>`
  * Request Body: `{ "status": "pending" | "processing" | "completed" | "cancelled" }`
- DELETE /api/stores/:id/orders/:orderId
  * Header: `Authorization: Bearer <token>`

G. REAL-TIME SERVER-SENT EVENTS (SSE)
- Connection URL:
  `GET /api/stores/:id/realtime?token=<supabase_access_token>`
- Protocol: HTML5 Server-Sent Events (`EventSource`)
- Automatic Events Emitted by Backend:
  * `ORDER_CREATED`: New customer checkout placed
  * `ORDER_STATUS_UPDATED`: Merchant transitioned order status
  * `ORDER_DELETED`: Order archived or removed
  * `STOCK_UPDATED`: Inventory adjusted or decremented by order
  * `PRODUCT_CREATED` / `PRODUCT_UPDATED` / `PRODUCT_DELETED`: Catalog updates
  * `STORE_UPDATED`: Store branding or settings changed
  * `STORE_DEPLOYMENT_UPDATED`: Live URL or deployment status modified
- Frontend Hook Implementation:
  Use `api.connectRealtime(storeId, (event) => { ... })` from `src/lib/api.ts`
  to update local React state and invalidate queries optimistically without page reloads.

H. PUBLIC STOREFRONT (BUYER ROUTE)
- GET /api/public/store/:slug
  * Public endpoint with zero authorization required.
  * Sanitized: Never exposes merchant `user_id`, private secrets, or internal logs.
  * Response:
    ```json
    {
      "store": {
        "id": "...",
        "name": "Obsidian Reserve",
        "slug": "obsidian-reserve",
        "businessType": "luxury",
        "currency": "₹",
        "selectedTemplateId": "obsidian-classic",
        "logoUrl": "...",
        "bannerUrl": "..."
      },
      "products": [
        { "id": 1001, "name": "...", "price": 99.99, "stock": 10, "emoji": "📦", "status": "active" }
      ],
      "template": { "id": "obsidian-classic", "name": "Obsidian Classic", ... }
    }
    ```

I. GOOGLE MAPS PLATFORM GEOLOCATION
- POST /api/maps/geocode
  * Request Body: `{ "address": "Marine Drive, Mumbai" }`
  * Response: `{ "success": true, "data": { "latitude": 18.9432, "longitude": 72.8234, "formattedAddress": "..." } }`
- POST /api/maps/place-details
  * Request Body: `{ "placeId": "ChIJ..." }`
  * Zero Secret Rule: Google Maps API key is kept strictly backend-side and NEVER returned to the client.

J. VERCEL STOREFRONT DEPLOYMENT
- POST /api/stores/:id/deploy
  * Header: `Authorization: Bearer <token>`
  * Response: `{ "message": string, "liveUrl": string, "deploymentId": string, "status": "READY" }`
- GET /api/stores/:id/deployment-status
  * Header: `Authorization: Bearer <token>`
  * Response: `{ "deploymentId": string, "status": "READY", "liveUrl": string }`
  * Zero Secret Rule: Vercel project tokens and deployment secrets are never returned in response bodies.

6. DATA CONTRACTS & TYPE INTERFACES
--------------------------------------------------------------------------------

The frontend TypeScript contracts must adhere to the following DTO shapes:

```typescript
// User Profile (Public Profiles)
export interface AuthenticatedUser {
  id: string; // Supabase auth.users UUID
  email: string;
  fullName?: string | null;
  ownerName?: string | null;
  avatarUrl?: string | null;
  role?: string | null;
}

// Store Configuration
export interface StoreDTO {
  id: string; // UUID
  userId: string; // auth.uid
  ownerId?: string | null;
  name: string;
  storeName?: string;
  slug: string;
  businessType: string;
  currency: string;
  logoUrl?: string | null;
  bannerUrl?: string | null;
  contactEmail?: string | null;
  contactPhone?: string | null;
  address?: string | null;
  formattedAddress?: string | null;
  latitude?: number | null;
  longitude?: number | null;
  placeId?: string | null;
  selectedTemplateId: string;
  liveUrl?: string | null;
  isDeployed?: boolean;
}

// Product (Frontend Model with numeric ID compatibility)
export interface FrontendProductDTO {
  id: number; // Client-facing numeric identifier
  backendId?: string; // PostgreSQL UUID
  name: string;
  price: number;
  discountPrice?: number | null;
  stock: number;
  emoji: string;
  category: string;
  description?: string | null;
  image?: string | null;
  imageUrl?: string | null;
  status: 'active' | 'draft' | 'archived';
}

// Order Item
export interface OrderItemDTO {
  id?: string | number;
  productId?: string | number | null;
  name?: string;
  productName?: string;
  quantity: number;
  unitPrice?: number;
  price?: number;
  emoji?: string;
  image?: string | null;
}

// Order (Frontend Model)
export interface FrontendOrderDTO {
  id: number; // Client-facing numeric identifier
  backendId?: string; // PostgreSQL BigSerial
  client_id?: number | null;
  storeId?: string;
  customerName: string;
  customerEmail?: string | null;
  customerPhone?: string | null;
  customerAddress?: string | null;
  paymentMethod?: string | null;
  productName: string;
  quantity: number;
  total: number;
  totalPrice?: number;
  status: 'pending' | 'processing' | 'completed' | 'cancelled';
  date: string; // Valid ISO-8601 string
  orderDate?: string;
  items?: OrderItemDTO[];
}
```

7. LOCALSTORAGE CONTRACTS & OFFLINE RESILIENCY
--------------------------------------------------------------------------------
LocalStorage is used purely as an offline fallback cache and UI state persist layer.
The backend PostgreSQL database remains the absolute source of truth.

| Storage Key            | Schema / Type    | Purpose & Invalidation Rules                              |
| :--------------------- | :--------------- | :-------------------------------------------------------- |
| `obsidian_token`       | String           | Supabase access token (cleared on logout)                 |
| `obsidian_session`     | JSON Object      | Session envelope: `{ access_token, user }`                |
| `obsidian_store`       | JSON (StoreDTO)  | Active store settings; refreshed via `/api/account/state` |
| `obsidian_products`    | JSON (Array)     | Catalog cache; synced via `/api/account/state` or SSE     |
| `obsidian_orders`      | JSON (Array)     | Orders cache; updated via `/api/account/state` or SSE     |
| `obsidian_cart_[slug]` | JSON (Array)     | Per-store shopping bag state (isolated by store slug)     |

8. SECURITY CONSTRAINTS & ZERO-SECRET EXPOSURE
--------------------------------------------------------------------------------
1. Secrets:
   - NEVER include `SUPABASE_SERVICE_ROLE_KEY` in frontend source code or bundles.
   - NEVER expose `VERCEL_API_TOKEN` or `GOOGLE_MAPS_API_KEY` to client components.
2. Cross-User Isolation:
   - Merchant endpoints check store ownership against `auth.uid()`.
   - Any attempt to modify another user's store returns `403 Forbidden`.
3. Sanitized Logs:
   - Do not log user passwords, tokens, or payment details in console output.
