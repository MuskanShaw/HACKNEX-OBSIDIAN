1. ARCHITECTURE OVERVIEW & PROTOCOL CONVENTIONS
================================================================================
The frontend is a digital commerce storefront engine built with Next.js 16,
React 19, and Tailwind CSS. All frontend interactions communicate with the backend
through a centralized API client (`frontend/src/lib/api.ts`).

- Protocol: HTTP/1.1 or HTTP/2, RESTful JSON APIs + SSE (Server-Sent Events)
- Default Port: 4000 (Backend)
- Frontend Dev URL: http://localhost:3000
- Content-Type: `application/json` (except asset uploads which use `multipart/form-data`)
- Character Set: UTF-8
- Base URL Resolution Order in Frontend:
    1. process.env.NEXT_PUBLIC_BACKEND_URL
    2. process.env.NEXT_PUBLIC_API_URL
    3. Fallback: https://obsidian-backend-1.onrender.com

3. AUTHENTICATION & IDENTITY HEADERS CONTRACT
================================================================================
The frontend supports standard JWT authentication while providing dual-header
fallback for seamless development and persistent merchant sessions.

1. JWT Authorization Header:
   On authenticated requests, the frontend sends:
   `Authorization: Bearer <jwt_token>`

2. User Identity Fallback Headers:
   Whenever an authenticated merchant session exists in local storage, the
   frontend automatically attaches the following identity headers on EVERY request:
   - `x-user-id` and `x-mock-user-id`: string (UUID or unique merchant ID)
   - `x-user-email` and `x-mock-user-email`: string (e.g. merchant@example.com)
   - `x-user-name` and `x-mock-user-name`: string (e.g. Jane Doe)

Backend Expectation:
If a valid JWT token is present in the `Authorization` header, verify and resolve
the merchant identity from the token payload. If the token is absent or expired,
fall back gracefully to resolving or auto-provisioning the merchant via the
`x-user-id` or `x-user-email` header.

4.10 Real-Time Server-Sent Events (SSE)
--------------------------------------------------------------------------------

1. Connect to Realtime Event Stream
   - Method: GET
   - Endpoint: `/api/stores/:storeId/realtime`
   - Query Parameters:
     * `token`: string (JWT token string when EventSource cannot pass custom headers)
   - Headers Sent by Client:
     * `Accept: text/event-stream`
   - Server Headers Sent Back:
     * `Content-Type: text/event-stream`
     * `Cache-Control: no-cache`
     * `Connection: keep-alive`
     * `Access-Control-Allow-Origin: *`
   - Behavior:
     Keep connection open, periodically send comment/ping to prevent socket timeouts:
     `: ping\n\n`
     When store events occur, push formatted SSE messages (see Section 6 for event types).

6. REAL-TIME EVENT STREAMING CONTRACT (SSE)
================================================================================
The frontend subscribes to the stream via:
`new EventSource("/api/stores/:storeId/realtime?token=...")`

The frontend registers listeners for these exact event names:
1. `ORDER_CREATED`: Dispatched when a buyer places a new order.
   Payload: { "order": { ... }, "remainingStock": number }
2. `ORDER_STATUS_UPDATED`: Dispatched when order changes status.
   Payload: { "orderId": ..., "status": "completed" }
3. `ORDER_UPDATED`: Dispatched on order edits.
   Payload: { "order": { ... } }
4. `ORDER_DELETED`: Dispatched when an order is deleted.
   Payload: { "deletedId": ... }
5. `STOCK_UPDATED`: Dispatched when product stock increments/decrements.
   Payload: { "productId": ..., "stock": number }
6. `PRODUCT_CREATED`: Dispatched when a new product is added.
   Payload: { "product": { ... } }
7. `PRODUCT_UPDATED`: Dispatched when product details change.
   Payload: { "product": { ... } }
8. `PRODUCT_DELETED`: Dispatched when a product is deleted.
   Payload: { "deletedId": ... }
9. `STORE_UPDATED`: Dispatched when store metadata changes.
   Payload: { "store": { ... } }
10. `STORE_DEPLOYMENT_UPDATED`: Dispatched when build status updates.
    Payload: { "status": "READY", "liveUrl": "https://..." }

Format in SSE Stream:
```
event: ORDER_CREATED
data: {"order":{"id":1727336640000,"customerName":"Alexander Vance","totalPrice":450}}

event: STOCK_UPDATED
data: {"productId":101,"stock":11}
```

7. ERROR HANDLING & HTTP STATUS CODES
================================================================================
The frontend parses errors by inspecting `res.json()`, searching for `message` or
`error`. Every 4xx/5xx error MUST be returned in standard JSON format:

```json
{
  "message": "Specific explanation of what went wrong"
}
```

Standard Status Codes Used:
- `200 OK`: Request succeeded
- `201 Created`: Resource successfully created
- `400 Bad Request`: Validation failure (missing required field, invalid format)
- `401 Unauthorized`: Missing or invalid Bearer token
- `403 Forbidden`: Authenticated user does not have permission for this store
- `404 Not Found`: Store, Product, or Order not found
- `409 Conflict`: Duplicate store slug or entity conflict
- `429 Too Many Requests`: Rate limit exceeded
- `500 Internal Server Error`: Unhandled backend exception
